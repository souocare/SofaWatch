# Database Migrations

SofaWatch uses Alembic to manage backend database schema evolution.

SQLite is the intended SofaWatch database for the self-hosted deployment model. Migrations must therefore be designed, reviewed, and tested with SQLite behavior in mind.

The migration system exists to provide a reproducible path from an older SofaWatch database schema to the current schema while preserving user data.

---

# 1. Principles

Database schema changes must be represented by Alembic migrations.

Do not treat:

```text
SQLAlchemy model changes
```

as sufficient by themselves.

The intended flow is:

```text
Change application model
        |
        v
Create Alembic migration
        |
        v
Review generated operations
        |
        v
Test upgrade
        |
        v
Run application tests
        |
        v
Commit model + migration together
```

An existing SofaWatch database should never depend on developers manually editing its schema.

---

# 2. Database Choice

SofaWatch uses:

```text
SQLite
```

This is an intentional product/deployment decision, not merely a temporary development database.

PostgreSQL is not part of the current roadmap.

Migration design should therefore prioritize correctness for SQLite rather than introducing complexity for database engines SofaWatch does not currently support.

See [Database Architecture](../architecture/database.md).

---

# 3. Alembic Location

Backend migration infrastructure lives under the backend project.

Conceptually:

```text
backend/
├── alembic/
│   ├── versions/
│   └── ...
├── alembic.ini
├── app/
└── tests/
```

Run Alembic commands from:

```text
backend/
```

with the backend virtual environment active.

---

# 4. Activate the Environment

If the virtual environment is at the repository root:

```bash
source ../.sofawatchvenv/bin/activate
```

If it is stored inside `backend/`:

```bash
source .sofawatchvenv/bin/activate
```

---

# 5. Apply All Migrations

To bring a database to the latest revision:

```bash
alembic upgrade head
```

This should normally be run after:

- cloning the project;
- pulling changes containing migrations;
- switching to a branch with newer schema requirements;
- upgrading a self-hosted installation.

---

# 6. Inspect Current Revision

```bash
alembic current
```

This shows the revision currently recorded for the configured database.

---

# 7. Inspect Migration Heads

```bash
alembic heads
```

For the normal linear SofaWatch migration history, there should ordinarily be one expected head.

Multiple heads indicate a branch in migration history and should be understood/resolved deliberately rather than ignored.

---

# 8. Inspect Migration History

```bash
alembic history
```

For more detail:

```bash
alembic history --verbose
```

This is useful when reviewing revision ordering or investigating upgrade paths.

---

# 9. Check for Unrepresented Model Changes

Alembic can compare SQLAlchemy metadata with the current database schema:

```bash
alembic check
```

This is useful before commits/releases to detect model changes that may require a migration.

A clean result does not replace reviewing migration logic or testing upgrades.

---

# 10. Creating a Migration

After intentionally changing SQLAlchemy models, create a revision with a meaningful description.

For example:

```bash
alembic revision --autogenerate -m "add example field"
```

This creates a migration under:

```text
alembic/versions/
```

Autogeneration is a starting point.

It is not an approval mechanism.

Always open and review the generated migration.

---

# 11. Review Every Autogenerated Migration

Before running a generated migration, inspect:

- `revision`;
- `down_revision`;
- `upgrade()`;
- `downgrade()`;
- table names;
- column names;
- types;
- nullability;
- defaults;
- indexes;
- foreign keys;
- unique constraints;
- data-loss operations.

Alembic cannot infer every application-level migration requirement.

For example, changing a column from nullable to non-nullable may require existing rows to be backfilled first.

---

# 12. Migration Naming

Use concise descriptions that explain the schema/data change.

Good examples:

```text
add movies to library
add auth sessions
add user admin flag
remove legacy local user concept
```

Avoid descriptions such as:

```text
changes
update db
fix
migration
```

The migration history should remain understandable months or years later.

---

# 13. Revision Chain

Every normal revision references its predecessor through:

```python
down_revision = "..."
```

Conceptually:

```text
revision A
    |
    v
revision B
    |
    v
revision C
    |
    v
HEAD
```

When two development branches independently create migrations from the same parent, merging the Git branches may produce multiple Alembic heads.

Do not resolve this by arbitrarily changing revision identifiers without understanding the migration history.

Depending on the situation, either:

- rebase/recreate one unpublished migration; or
- create an explicit Alembic merge revision.

For migrations that may already exist in real installations, preserve migration history and use a proper forward migration strategy.

---

# 14. Migrations Are Part of the Application Contract

Once a migration has been published and may have been applied by another installation, treat it as immutable history.

Do not casually edit an old migration to change what it does.

Instead, add a new migration that moves the schema/data from the old state to the new desired state.

Editing already-applied migration history creates installations that claim to be on the same revision while having different schemas.

---

# 15. Development-Only Unpublished Migrations

During local development, a migration that has never been merged/shared/applied outside the development branch may sometimes be safely regenerated.

Before doing so, confirm that it is genuinely unpublished.

Once uncertain, prefer a new forward migration.

---

# 16. Schema and Data Migrations

Some changes only modify schema:

```text
add table
add column
add index
```

Others require transforming existing data:

```text
populate new ownership field
convert legacy user representation
normalize values
migrate relationships
```

A migration may contain both schema and data operations when the transition requires them.

Data migrations should be:

- deterministic;
- explicit;
- safe for existing installations;
- independent from current runtime service behavior where possible.

---

# 17. Avoid Importing Application Services into Migrations

Migrations are historical artifacts.

Avoid depending on current application services or domain code from an old migration.

For example, avoid:

```python
from app.services.some_future_service import SomeService
```

inside migration history.

Application code evolves.

A migration written today must still be able to run later even if services have been refactored.

Prefer Alembic operations and SQL/SQLAlchemy constructs that are self-contained within the migration.

---

# 18. SQLite Considerations

SQLite supports many schema operations directly, but not every alteration works like larger client/server databases.

Alembic may need batch operations for some changes.

Typical pattern:

```python
with op.batch_alter_table("example") as batch_op:
    batch_op.add_column(...)
```

Use batch mode when required by the actual operation and Alembic/SQLite behavior.

Do not mechanically use it for every migration if a normal operation is sufficient.

---

# 19. Foreign Keys

SofaWatch explicitly enables SQLite foreign-key enforcement using:

```sql
PRAGMA foreign_keys=ON
```

Migration design must respect real foreign-key relationships.

When changing referenced tables/columns, consider:

- existing rows;
- delete behavior;
- migration ordering;
- temporary invalid states;
- constraint recreation.

A migration that works only when foreign-key enforcement is accidentally disabled is not acceptable.

---

# 20. Adding a Nullable Column

A simple new optional field may often be introduced directly:

```text
existing rows
    |
    v
new column = NULL
```

This is usually straightforward, but still review whether application code correctly handles older rows with no value.

---

# 21. Adding a Required Column

Adding a non-nullable column to a table with existing rows requires a migration strategy.

A common safe sequence is:

```text
1. Add column as nullable or with a safe temporary default
2. Backfill existing rows
3. Verify all rows have a value
4. Enforce NOT NULL
5. Remove temporary default if inappropriate
```

The exact operations depend on the feature and SQLite constraints.

Do not assume an empty production/self-hosted database.

---

# 22. Defaults

Distinguish between:

```text
Python/application default
```

and:

```text
database/server default
```

They are not interchangeable.

An application default affects rows created through application code.

A database default affects inserts performed at the database level when the column value is omitted.

Use database defaults only when they are actually part of the persistence contract.

---

# 23. Renaming Columns

A rename should preserve data.

Do not model a rename as:

```text
drop old column
add new column
```

unless data loss is explicitly intended.

Use the appropriate Alembic operation/SQLite-compatible strategy.

---

# 24. Renaming Tables

The same principle applies to tables.

A conceptual rename should preserve:

- rows;
- indexes;
- foreign-key relationships;
- constraints.

Review generated SQL/operations rather than assuming autogenerate understands application intent.

---

# 25. Removing Columns or Tables

Destructive operations deserve additional review.

Before dropping data, ask:

- Is the feature genuinely removed?
- Is the data needed for migration?
- Is rollback expected?
- Could an older installation still depend on it?
- Should data first be copied into a replacement structure?

For legacy cleanup, remove data/schema only after the replacement model is established.

---

# 26. Multi-User Migrations

SofaWatch is now multi-user.

Schema changes involving user-owned data must preserve ownership.

Important user-scoped areas include:

- Library;
- Episode progress;
- Episode watch events;
- Movie watch events;
- ratings;
- authentication sessions;
- recovery-related state.

Do not introduce migrations that silently assign existing data to the wrong user or detach ownership.

---

# 27. Legacy Local User Migration

The historical `is_local` / fixed local-user concept has been removed.

The development migration strategy converted the existing development user into a real account while preserving the same internal user ID.

That preservation matters because user-owned rows reference the internal `user_id`.

Conceptually:

```text
Legacy user
    id = X
      |
      v
Real authenticated user
    id = X
      |
      +--> Library preserved
      +--> Progress preserved
      +--> History preserved
      +--> Ratings preserved
```

Do not reintroduce `is_local` or create a replacement user with a new ID as part of future migration work.

---

# 28. Internal IDs and Provider IDs

SofaWatch uses internal IDs as domain/database identity.

Provider identifiers such as:

- TMDB;
- future TVDB;
- IMDb;

must not replace internal primary keys during migrations.

Future provider-mapping migrations should preserve:

```text
SofaWatch internal entity
        |
        +--> external TMDB identifier
        +--> external TVDB identifier
        +--> external IMDb identifier
```

rather than turning a provider ID into the application's primary identity.

---

# 29. Library Constraints

Library entries may refer to a Show or a Movie according to the current polymorphic design.

The conceptual invariant is:

```text
show_id XOR movie_id
```

Meaning:

```text
Show entry:
show_id  = value
movie_id = NULL

Movie entry:
show_id  = NULL
movie_id = value
```

Never both and never neither.

Migrations affecting Library must preserve this invariant.

---

# 30. Watch Event Migrations

Viewing history is event-based.

Do not collapse multiple historical viewing events into one row during migration unless a deliberate data-model migration explicitly requires it.

Rewatches are real separate events.

Preserve:

- event identity;
- media/episode relationship;
- user ownership;
- `watched_at`.

Derived values such as `watch_count` should remain consistent with event history.

---

# 31. Authentication Migrations

Authentication-related migrations require extra care.

Do not expose or weaken:

- password hashes;
- session credential hashes;
- recovery token hashes;
- handoff credential hashes.

Persistent authentication credentials should remain represented server-side by hashes rather than plaintext values.

Schema migration logs/output should not contain secret credential material.

---

# 32. Creating a Fresh Development Database

For a genuinely disposable local database, you may create a fresh database and apply:

```bash
alembic upgrade head
```

This verifies:

```text
empty database -> current schema
```

It is useful, but it is only one migration path.

Do not confuse this with upgrade compatibility for existing installations.

---

# 33. Testing Upgrade Compatibility

Before important releases, SofaWatch should also test:

```text
older real schema/data
        |
        v
alembic upgrade head
        |
        v
current application
```

Use a representative snapshot of an older SofaWatch database.

Verify that important data survives.

---

# 34. Legacy Database Upgrade Checklist

For a representative old database, verify at least:

- Alembic reaches `head`;
- user IDs are preserved;
- users remain valid;
- Library entries remain associated correctly;
- Episode progress survives;
- Episode watch history survives;
- Movie watch history survives;
- ratings survive;
- other user-scoped relationships survive;
- authentication migration behaves as intended;
- foreign-key checks remain clean;
- the current backend can open and use the upgraded database.

This should eventually become an automated or repeatable release test.

---

# 35. Migration Test Data

A useful old-database fixture should contain more than an empty schema.

Include representative data such as:

```text
user
show
movie
library entries
seasons
episodes
episode progress
episode watch events
movie watch events
ratings
```

and any historical structures relevant to the migration being tested.

The objective is to detect data-preservation failures, not only SQL syntax errors.

---

# 36. Downgrades

Alembic migrations include:

```python
downgrade()
```

where practical.

Downgrade support is useful during development and for understanding reversibility, but it must not create false confidence.

Some migrations are inherently destructive or cannot reconstruct data removed during upgrade.

If downgrade cannot safely restore data, document/implement the most honest behavior possible rather than pretending reversibility exists.

Production rollback strategy may involve restoring a database backup rather than relying exclusively on Alembic downgrade.

---

# 37. Test a Downgrade During Development

For a new migration where downgrade is intended to work, a useful local cycle is:

```bash
alembic upgrade head
alembic downgrade -1
alembic upgrade head
```

Only do this against disposable/test data unless you understand the downgrade's data implications.

---

# 38. Do Not Downgrade a Valuable Database Casually

Never use a real development/production-like database as a migration experiment without a backup.

A downgrade may intentionally remove columns/tables/data introduced by a migration.

---

# 39. Migration Backups

Before applying migrations to an important self-hosted database, a future production upgrade process should create a safe SQLite backup.

The final backup strategy is still planned.

Because SQLite may use WAL mode, production backup guidance must account for SQLite's actual consistency requirements rather than copying files blindly while the database is active.

See [Database Architecture](../architecture/database.md).

---

# 40. Migration Transactions

Use Alembic/SQLAlchemy transaction behavior appropriately, but do not assume every SQLite schema operation has identical transactional semantics to normal DML.

For complex migrations, test failure behavior against SQLite.

A migration should avoid leaving the database in an ambiguous partially transformed state where possible.

---

# 41. Data Backfills

For a backfill:

- define exactly which rows are affected;
- avoid relying on current wall-clock time unless intended;
- avoid provider/network calls;
- avoid non-deterministic ordering;
- make ownership explicit;
- verify row counts where useful.

A migration should be runnable without TMDB/TVDB/internet access.

---

# 42. No External Provider Calls in Migrations

Never require:

```text
TMDB
TVDB
IMDb
```

to be online for a schema migration.

Provider metadata can be refreshed later through application/provider synchronization.

Database migration and external metadata synchronization are separate concerns.

---

# 43. Migration Logging

Migration output should help diagnose schema transitions without exposing sensitive application data.

Do not print:

- passwords;
- hashes unnecessarily;
- tokens;
- session credentials;
- recovery credentials;
- provider secrets.

For data migrations, aggregate counts are usually more appropriate than dumping row contents.

---

# 44. Alembic and Application Startup

Do not silently mutate the schema from normal application model initialization as a substitute for Alembic.

The desired operational contract is explicit:

```bash
alembic upgrade head
```

followed by application startup.

This keeps upgrades observable and reproducible.

---

# 45. Migration and Model Changes in the Same Commit

When a model change requires a migration, normally commit together:

```text
SQLAlchemy model
Alembic migration
related schemas/services
tests
```

Avoid merging application code that requires a schema which no migration creates.

---

# 46. Migration Review Checklist

Before accepting a migration, check:

```text
[ ] revision ID exists
[ ] down_revision is correct
[ ] only intended schema changes are present
[ ] SQLite behavior is valid
[ ] existing rows are handled
[ ] nullability transition is safe
[ ] defaults are intentional
[ ] indexes/constraints are correct
[ ] foreign keys remain valid
[ ] user ownership is preserved
[ ] no unintended data loss
[ ] no external API dependency
[ ] secrets are not exposed
[ ] downgrade is reasonable/honest
[ ] upgrade works from predecessor
[ ] current application tests pass
```

---

# 47. Release Migration Checks

Before an important release:

```bash
alembic current
alembic heads
alembic check
```

Then test:

```text
fresh database -> head
```

and, when relevant:

```text
representative older database -> head
```

The latter is especially important as SofaWatch moves toward stable self-hosted releases.

---

# 48. Multiple Heads

If:

```bash
alembic heads
```

returns multiple active heads unexpectedly, stop and inspect the revision graph.

Useful command:

```bash
alembic history --verbose
```

Do not simply choose one head and ignore the other.

Both branches may contain required schema changes.

---

# 49. Merge Revisions

When two legitimate published migration branches must be reconciled, Alembic supports merge revisions.

Conceptually:

```text
        B
       / \
      A   D
       \ /
        C   (conceptual only)
```

More accurately, a merge revision can reference multiple previous heads.

Use this when preserving both migration histories is the correct solution.

For unpublished branch-local migrations, rebasing/recreating may produce a cleaner linear history.

Choose based on whether migration history has escaped the branch.

---

# 50. Autogenerate Limitations

Alembic autogenerate may not correctly infer intent for:

- renames;
- data transformations;
- semantic enum/value changes;
- application-level invariants;
- complex constraints;
- provider-ID migrations;
- ownership migrations.

For example, a rename may appear as:

```text
drop old column
add new column
```

which could destroy data.

Always review.

---

# 51. Constraint Naming

When adding constraints/indexes, use clear stable names where the project conventions require explicit naming.

Stable names improve:

- migration readability;
- debugging;
- future alteration/removal.

Do not rely on opaque generated names when they make future migration operations fragile.

---

# 52. Data Integrity Checks

For important migration work, SQLite integrity checks can be useful.

Examples:

```sql
PRAGMA integrity_check;
```

and:

```sql
PRAGMA foreign_key_check;
```

These are especially useful when testing a representative upgraded database.

They should complement application-level verification rather than replace it.

---

# 53. Server Diagnostics

SofaWatch's administrative database diagnostics may expose safe operational information such as:

- database engine;
- size;
- connectivity;
- integrity status;
- foreign-key status;
- Alembic revision.

These diagnostics are not a replacement for migration tooling.

Alembic remains the schema-evolution authority.

---

# 54. Failed Migration During Development

If a new unpublished migration fails against disposable development data:

1. read the actual failure;
2. inspect the migration;
3. determine whether the schema or data assumption is wrong;
4. fix the migration;
5. recreate/reset only disposable data if needed;
6. test again from the predecessor revision.

Do not keep stacking "fix migrations" on top of a migration that has never left your development branch unless doing so provides a real compatibility benefit.

---

# 55. Failed Migration on Existing Valuable Data

Do not repeatedly experiment against the only copy of valuable data.

Preserve the database and investigate using a copy/snapshot.

A future production upgrade process should define:

```text
backup
  |
  v
migration
  |
  v
verification
  |
  +--> success -> continue
  |
  +--> failure -> restore/recovery procedure
```

---

# 56. Migration Files Are Code

Treat migration files with the same standards as application code:

- readable;
- minimal;
- reviewed;
- deterministic;
- tested;
- no dead experimental operations;
- no unexplained hacks.

A migration may only run once per installation, but it can determine whether years of user data survive an upgrade.

---

# 57. Future Provider Architecture Migrations

Adding TVDB/IMDb/external identifiers may require new persistence structures.

Prefer extensible mappings rather than spreading columns such as:

```text
tvdb_id
imdb_id
```

through unrelated business tables without an architecture decision.

The intended long-term concept is:

```text
Internal Media Entity
        |
        v
External Identifier Mapping
        |
        +--> TMDB
        +--> TVDB
        +--> IMDb
```

The exact schema should be designed when provider architecture work begins.

Do not create speculative migrations before the feature exists.

---

# 58. Future Backup Integration

Once SofaWatch has a formal backup feature, migration-aware upgrade workflows should integrate with it.

Potential flow:

```text
Pre-upgrade backup
        |
        v
Validate backup
        |
        v
Apply migrations
        |
        v
Run integrity checks
        |
        v
Start application
```

Do not document backup status in Server diagnostics as functional until a real backup strategy exists.

---

# 59. Future Migration Automation

As the release process matures, useful automated checks may include:

- fresh SQLite migration to head;
- `alembic check`;
- one-head assertion;
- representative legacy database upgrade;
- `PRAGMA integrity_check`;
- `PRAGMA foreign_key_check`;
- post-upgrade smoke tests.

Introduce automation when it protects real release risk rather than merely increasing tooling.

---

# 60. What "Migration Complete" Means

A schema change is not complete when:

```text
the SQLAlchemy model compiles
```

or merely when:

```text
alembic revision --autogenerate
```

succeeds.

A migration-related change is complete when:

```text
model is correct
+
migration is reviewed
+
upgrade works
+
existing data is handled
+
SQLite constraints remain valid
+
focused tests pass
+
relevant full backend suite passes
```

For release-critical migrations, representative legacy upgrade testing should also pass.

---

## Quick Reference

Apply latest migrations:

```bash
alembic upgrade head
```

Current revision:

```bash
alembic current
```

Current head(s):

```bash
alembic heads
```

History:

```bash
alembic history --verbose
```

Check model/schema differences:

```bash
alembic check
```

Create an autogenerated revision:

```bash
alembic revision --autogenerate -m "describe change"
```

Downgrade one revision:

```bash
alembic downgrade -1
```

Upgrade again:

```bash
alembic upgrade head
```
